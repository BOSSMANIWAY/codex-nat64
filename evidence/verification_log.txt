Phase 1 - Source review
-----------------------
network-proxy/src/policy.rs, is_non_public_ipv6():
  * decodes only IPv4-mapped / IPv4-compatible addresses via Ipv6Addr::to_ipv4();
  * no handling of RFC 6052 NAT64 Well-Known Prefix 64:ff9b::/96;
  * 64:ff9b::a14:a (embeds 10.20.0.10) falls through every check -> "public".
Related: is_private_network_ip() in the same file shares the to_ipv4() blind spot.

Phase 4 - Stage B (end-to-end differential test of the real proxy binary)
-------------------------------------------------------------------------
Harness: stage_b_local/run.sh inside `unshare -rn` (user+network namespace, no root):
  * dns64_server.py answers the sandbox resolver addresses on :53;
    web.internal.corp -> AAAA 64:ff9b::a14:a (DNS64 synthesis, embeds 10.20.0.10);
    plainv4.internal.corp -> A 10.20.0.10; publicnat.internal.corp -> AAAA 64:ff9b::808:808;
  * backend.py serves a marker body from 10.20.0.10:80, [64:ff9b::a14:a]:80 and
    [64:ff9b::808:808]:80;
  * `ip -6 route add local 64:ff9b::/96 dev lo` makes the WKP locally routable -
    the same flow a NAT64 gateway produces from the proxy's point of view;
  * all three hostnames are on the proxy allowlist (stage_b_local/cfg.json);
  * real codex-network-proxy binary, RUST_LOG=info, HTTP proxy on 127.0.0.1:8080.

Conclusion
----------
The private-address gate of codex-network-proxy is bypassable through the RFC 6052
NAT64 Well-Known Prefix end-to-end with the real binary. The one-line WKP decode fix
closes the bypass and does not break legitimate NAT64 traffic.
